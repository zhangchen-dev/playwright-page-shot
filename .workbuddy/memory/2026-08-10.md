# 2026-08-10 工作记录

## 内置浏览器 target=_blank 打不开新窗口 — 根因排查

**现象**：应用内（Electron `<webview>` 模式）点击"帮助中心"（`target="_blank"`，href=`/helpapp/#/help-main`）无法打开新窗口页面；外部浏览器模式（Playwright Chromium）正常。用户误以为是 Playwright 导致。

**架构**：两套浏览器。
- 应用内模式：`renderer/panel.html` 的 `<webview id="previewWebview">`（当前带 `webpreferences="allowpopups"`），导航由 `renderer/modules/recording/internal/webview-recording.js` 的 `navigateInAppBrowser` 负责。
- 外部模式：`src/browser-manager.js` 用 Playwright 启动真实 Chromium，`context.on('page')` 原生支持多 tab。

**根因（3 点）**：
1. `panel.html:101` 的 `webpreferences="allowpopups"` 是旧 Fix 2（`.trae/documents/fix-rerecord-nav-and-webview-newtab.md`）遗留。当前 main.js 已迁移到 Electron 22+ 的 `setWindowOpenHandler`（main.js:107-142，挂在 `did-attach-webview` 的 `wc` 上，返回 `{action:'deny'}` 后再 `wc.loadURL` 当前 webview）。`allowpopups` 与 setWindowOpenHandler 冲突，会让 webview 弹出**脱离应用 UI 的未管理原生 BrowserWindow** → "打不开/无法展示"。
2. `setWindowOpenHandler` 只挂在 `did-attach-webview` 的 `wc` 上（main.js:107）。Electron 对 `<webview>` 弹窗，`did-attach-webview` 方式不一定可靠触发（SO: webview setWindowOpenHandler not called）；更稳的是 `app.on('web-contents-created')` 全局挂。
3. 即便拦截成功，当前逻辑是 `wc.loadURL` **替换当前 webview 页面**，并非用户期望的"新 tab"。

**与 Playwright 无关**：Playwright 只在外部模式用，且那里多 tab 正常。问题纯在 Electron webview 弹窗处理。

**沙箱限制**：本地 Electron 的 GPU/network 子进程在沙箱里崩溃（exit 143），webview 无法实跑渲染，未能做真实点击验证；结论基于代码 + Electron 文档/社区。

**推荐修复方向**：① 去掉 `allowpopups`；② 改用 `app.on('web-contents-created')` 全局挂 `setWindowOpenHandler`；③ 拦截后"开新 tab"。

**已实现（应用内多 tab，用户拍板方向）**：
- `main/main.js`：`did-attach-webview` 上的 setWindowOpenHandler 改为 `app.on('web-contents-created')`（仅 type==='webview'），拦截 target=_blank/window.open 后 deny 原生弹窗 + IPC `webview-new-window` 通知渲染进程。
- `main/preload.js`：`onWebviewOpenWindow`(webview-open-window) → `onWebviewNewWindow`(webview-new-window)。
- `renderer/panel.html`：#previewContainer 内加 #tabBar + #tabPages，原 #previewWebview 包进 data-tab-id="main"；**去掉 webpreferences="allowpopups"**。
- `renderer/styles/layout.css`：tab-bar / tab / tab-pages / webview-tab-page 样式。
- 新增 `renderer/modules/common/tabs.js`：openTab/activateTab/closeTab/renderTabBar/initTabs/getActiveWebview；新 tab 为独立 webview 填满容器。
- `webview-controls.js`：移除旧同页导航监听，initBrowserModeControls 内调用 initTabs()。
- `webview-recording.js`：navigateInAppBrowser 加载前 activateTab('main')。
- 语法已用 node --check 验证通过。沙箱无法渲染 webview（GPU 进程崩溃），需在用户机器 `npm start` 实测：应用内打开 UAT → 点"帮助中心"应右侧新增 tab 展示帮助页。

## 灰屏回归修复（同一次多 tab 改动引入）

**现象（用户线下反馈）**：应用内打开页面"完全是灰色，看不到内容"。

**根因**：panel.html 把 `#previewWebview` 包进 `.webview-tab-page`（新增的 tab 页容器，CSS 为 `display:block`）。原本 `.webview-scroll-wrapper` 是 `.preview-container`（flex 列）的**直接子元素**，`flex:1` 能撑满高度；改动后它变成 `display:block` 容器的子元素，`flex:1` 失效 → 滚动/缩放层高度塌缩 → webview 容器高度塌缩 → 整片灰屏看不到内容。

**修复（layout.css）**：
- `.webview-tab-page.active` 由 `display:block` 改为 `display:flex; flex-direction:column`，让内部 `.webview-scroll-wrapper(flex:1)` 重新撑满（等价于改动前"scroll-wrapper 直接挂在 flex 列容器下"的效果）。
- `.webview-scroll-wrapper` 加 `min-height:0`（flex 子项允许收缩）。
- 新 tab 的 `.preview-webview-inner.tab-webview` 加 `flex:1 1 auto; min-height:0` 填满容器。

**排查排除项**：main.js 的 `web-contents-created` 拦截只 deny 弹窗 + IPC 通知，不阻断 webview 正常加载；preload 通道名 `webview-new-window` 与 main.js 一致；`activateTab` 导入正常、导航 `webview.src=url` 未断。均非灰屏原因。

## 多 tab 不生效 + 切回重载（同一根因）

**用户实测反馈**：① 点"帮助中心"后 tab 栏只有 1 个 tab；② 切回上一页会重新加载。

**根因（同一个）**：新 tab 根本没被创建。点 `target=_blank` 时拦截没真正触发"开新 tab"，链接直接落到了那唯一的主 webview 上导航（所以"切回"= 重新导航主 webview = 重载）。

**真凶**：上一轮把拦截从 `did-attach-webview` 换成了 `app.on('web-contents-created')` + `getType()==='webview'` 判断。本应用实测 `web-contents-created` 这条路径不生效（最初版本就是用 `did-attach-webview` 触发的，当时只是"导航当前页"）。`npm start` = `electron .` 跑 `main/main.js` 源码，确认源码生效，非打包产物滞后。

**修复**：
- `main/main.js`：`app.on('web-contents-created')` 改回 `panelWindow.webContents.on('did-attach-webview', (event, wc) => {...})`，去掉 `getType()==='webview'` 守卫；拦截后 `deny` + IPC `webview-new-window`。
- `tabs.js` `openTab`：把 `activateTab(id)` 移到 `wv.loadURL(url)` **之前**，确保新 webview 在可见容器里再加载（隐藏 webview 可能不触发加载/切回重载）。
- 更新 `webview-controls.js` 注释（web-contents-created → did-attach-webview）。

**预期行为**：点帮助中心 → 右侧新增独立 tab（独立 webview）并加载帮助页，主 tab 保持原页面；tab 栏出现多个 tab，可切换、× 关闭；切回已加载的 tab 不再重载（各自独立 webview 保留状态）。仍受沙箱 GPU 限制无法本地实跑，需用户 `npm start` 验证。

→ 证明 Electron 34 `<webview>` 的 `setWindowOpenHandler` 确实不拦 `target="_blank"`，但 **DOM 层捕获阶段注入是可行的**。

**最终链路**（三段）：

2. 注入脚本调用 `window.__recSendToHost('rec-new-tab', {url})`（项目已有的 `src/inject/webview-preload.js` 用 contextBridge 暴露，内部是 `ipcRenderer.sendToHost`）；

**配套改动**：
- `requestNewTab()` 加 1s 同 URL 去重（sendToHost / main-ipc 两条通道可能同时触发）。
- `console-message` 默认只透传 `[rec-` 开头的日志，避免业务页面日志刷屏；`REC_VERBOSE_WEBVIEW_LOG=1` 可开全量。

**经验**：Electron `<webview>` 里主世界注入脚本要和宿主通信，别用 console 解析，优先复用 preload 的 `contextBridge + ipcRenderer.sendToHost` → 宿主 `webview.addEventListener('ipc-message')`。

## 根因确诊 + 调研结论（15:21）

**为什么 setWindowOpenHandler / new-window 都"没反应"：**
经外网核实（Electron issue errorism.dev #30680 类），这是 Electron 已知行为：
> 当 `nativeWindowOpen` 处于启用状态时，点击 `target="_blank"` 链接和 `window.open()`
> **都不会发出任何事件**（既不触发 webview 宿主的 `new-window`，也不触发 `setWindowOpenHandler`）。
Electron 新版 `nativeWindowOpen` 默认即 true。我们既没在 webview 上显式关掉它，
`allowpopups` 也救不了 → 主进程/宿主元素的所有拦截全部静默失败，表现就是"点击没反应"。
这同时解释了为什么 DOM 注入（在页面 JS 里拦）能成功：`[rec-intercept] 拦截 target=_blank` 出现过，
因为它不依赖 Electron 的 window-open 机制。

**其他项目标准做法（调研）：**
- Electron 22+ 官方对 `<webview>` 拦截新窗口 = `allowpopups` + `wc.setWindowOpenHandler`，且 `nativeWindowOpen` 必须为 false。
- `new-window` 事件在 BrowserWindow webContents 上 Electron 22 已移除，但 `<webview>` 仍可用，前提是 nativeWindowOpen=false。
- 多 tab 展示：要么 `event.newGuest` 接管，要么自建 `<webview>`/BrowserWindow。

**关键复用点（被验证可用的通道）：**
录制选元素用的就是 webview preload `contextBridge` 暴露的 `window.__recSendToHost`
（`ipcRenderer.sendToHost` → 宿主 webview 的 `ipc-message`）。主 webview 的 preload 由
`webview-controls.js:88-93` 在运行时 `setAttribute('preload', ...)` 挂上，所以 `__recSendToHost=function`
确实可用。录制没坏 → 说明这条"注入→__recSendToHost→ipc-message→宿主"通道可靠。
→ 最终方案应以这条通道为主，DOM 注入负责"拦到点击"，__recSendToHost 负责"送达"。

**卡顿（页面卡）根因：独立环境问题，与拦截无关。**
日志 `Unable to move the cache: 拒绝访问(0x5)` / `Gpu Cache Creation failed: -2` 表明 userData 缓存目录
不可写 → Electron 退化为软件渲染 → 卡。属环境/权限，后续单独处理（--disable-gpu / 修缓存目录权限 / 新tab改BrowserWindow）。

## 根因确诊② + 最终修复（15:44）

**真因（上一轮"点击没反应"的真正原因）**：

**改动文件**：`main/main.js`（注入脚本 + console-message 解析标记 + 注入成功日志）、

## 根因确诊③ + 修复（15:55）

**真因（之前"点击没反应"的最后一个 bug）**：
`REC_INTERCEPT_JS` 中点击拦截的判定写成了
`a.getAttribute('href')` + `/^https?:/i.test(getAttribute('href'))`。
银行"帮助中心"链接是 `<a href="/helpapp/#/help-main" target="_blank" rel="opener">`，
`getAttribute('href')` 返回的是**相对路径**字符串 `/helpapp/#/help-main`，
用 `^https?:` 校验必然失败 → `if` 不成立 → 既不打印 catch 也不开 tab。
（14:59 那版能"有反应"是因为当时拦截后直接 `location.href` 原地跳、没做 https 校验；
后来加校验时把 `a.href` 误写成 `a.getAttribute('href')`，相对路径这一下漏了。）

**修复**：
- 点击判定改用 `a.href`（浏览器已解析的绝对地址 `https://.../helpapp/#/help-main`）。
- 新增 `toAbs(url)`：用 `new URL(url, location.href).href` 把相对路径归一化为绝对，
  同时用于 `window.open` 覆盖分支（框架若以相对路径调 window.open 也能兜住）。
- 两个分支都先归一化再校验 `^https?:`。

**为什么真实浏览器可以、应用不行（用户疑问解答）**：
真实浏览器中 `target="_blank"` 是浏览器原生能力，点击即由浏览器新开 tab，无需应用代码；
Electron `<webview>` 中该原生窗口打开被沙箱压制（`nativeWindowOpen` 行为下事件不冒泡到应用代码），
必须手动拦截点击自己开 tab —— 而我们的拦截器判定标准写错（相对路径），等于装上了但判题错了。

## 终极根因 + 换方案（与上一节不同！）

**新发现的根因（DOM 注入方案的彻底失败原因）**：
- `renderer/panel.html` 第 106 行（之前）写的是
  `<webview ... webpreferences="allowpopups">`
- `allowpopups` 这个 webpreference 让 `<a target="_blank">` 点击**直接走 Electron native 弹窗流程**
  （开新 BrowserWindow），**根本不触发**：
  1. 页面里的 click 事件（页面 JS 收不到点击）
  2. `<webview>` 标签的 `new-window` 事件（被 native 流程吃掉）
  3. `setWindowOpenHandler` / `wc.on('new-window')`（webContents 级别）
- 所以前面所有"注入拦截脚本 + console bridge + sendToHost"都看到 `[rec] injected` 成功日志，
  但**永远不会有 `[rec] catch target=_blank`** —— 因为页面 JS 根本没收到 click。
- 新 tab 的 webview 同样设了 `allowpopups`，新 tab 内再点链接也会重新走 native 弹窗。

**新方案（Electron 标准做法）**：
1. `panel.html`：`<webview id="previewWebview">` 去掉 `webpreferences="allowpopups"`。
2. `tabs.js openTab`：新建 webview 也去掉 `allowpopups`，注释里写明原因。
3. `main/main.js`：删除 REC_INTERCEPT_JS 整块 + console 解析逻辑，
   在 `did-attach-webview` 回调里给 `wc` 注册 `wc.on('new-window', ...)`：
   ```js
   wc.on('new-window', (evt, url, frameName, disposition) => {
     if (evt && evt.preventDefault) evt.preventDefault();
     panelWindow.webContents.send('webview-new-window', { sourceWebviewId: wc.id, url });
   });
   ```
   webContents 级别事件，是 Electron 引擎层最底层，覆盖 `<a target="_blank">` + `window.open`，
   与页面 JS、preload、iframe、single-spa 路由无关。
4. `tabs.js`：`bindNewWindow` 从"备份通道"升为"主通道"；
   `bindNewTabIpc` 降为"备用"（仅在 webContents 事件未被触发时使用）。

**为什么之前所有日志只看到 `[rec] injected` 没看到 `catch target=_blank`**：
注入成功了，但 `<a target="_blank">` 点击根本到不了页面 JS 事件循环 —— native 弹窗流程在浏览器
引擎层就接管了，页面收不到 click 事件。

**验证预期（重跑）**：
终端依次出现
`[main] did-attach-webview 触发, webviewId: 2`
→ 用户点"帮助中心" →
`[main] new-window webviewId=2 disposition=foreground-tab url=https://xft2-web-home-uat.cmburl.cn/helpapp/#/help-main`
→ `[tabs] new-window 事件 url=...` → 右侧出现新 tab，原页面保留。

**残留进程陷阱**：
应用关窗口 = 最小化到托盘，无单实例锁，用户机器经常堆积 6+ 个 electron.exe 导致 `npm start`
不起新进程、新代码不加载。已多次 taskkill /f /im electron.exe 清除。

## ERR_ABORTED (-3) 根因 + 修复（new-window 方案的下一个拦路虎）

**现象**：去掉 `allowpopups` 后，主 webview 加载 URL 报
```
Error occurred in handler for 'GUEST_VIEW_MANAGER_CALL': Error: ERR_ABORTED (-3)
loading 'https://xft2-web-home-uat.cmburl.cn/'
```

**根因**：`<webview>` 标签的关键属性（preload / partition / src）在 webview 已 attach 或
正在加载时被运行时修改，Electron 会销毁当前 webContents 并 abort 当前 navigation。
原来的实现：
```js
// webview-controls.js:91（已删）
api.getWebviewPreloadPath().then((preloadUrl) => {
  if (preloadUrl) {
    _wv.setAttribute('preload', preloadUrl);  // ← 触发 abort
  }
});
```
IPC 是异步的，setAttribute 在用户点 → 之后才到达，webview 已经在加载 URL，被迫 abort。

**修复（3 处协同改动）**：
1. **`main/preload.js`**：用 `path.join(__dirname, '..', 'src', 'inject', 'webview-preload.js')`
   同步算出 `WEBVIEW_PRELOAD_FILE` 常量；`getWebviewPreloadPath` 改为返回
   `Promise.resolve(WEBVIEW_PRELOAD_FILE)`；新增 `getWebviewPreloadPathSync()` 同步接口。
2. **`renderer/panel.html`**：把静态 `<webview id="previewWebview" ...>` 改为
   `<div id="previewWebviewSlot" class="preview-webview-inner">` 占位。
3. **`renderer/modules/common/webview-controls.js`**：新增 `ensurePreviewWebview()`，
   在 `initBrowserModeControls()` 第一行同步调用：`document.createElement('webview')`
   → `setAttribute('partition')` + `setAttribute('preload')` → `slot.replaceWith(wv)`。
   preload 在 append 之前已设好，**绝对安全**。

`tabs.js openTab` 已有的写法（`createElement` → setAttribute → await preload →
`appendChild`）也安全，因为 await 完成后再 appendChild。

**验证预期**（重跑）：
终端依次出现
`[main] did-attach-webview 触发, webviewId: 2`
→ 用户点"帮助中心" →

→ `[tabs] new-window 事件 url=...` → 右侧出现新 tab，原页面保留。

**现象**：在 renderer JS 里写 `console.log('[panel] xxx')`，但终端看不到这行。

## 真正的最终根因：<webview> 的 nativeWindowOpen 默认是 true！

**症状**：去掉 `allowpopups` 后，`[main] new-window` 仍不触发。
**根因（Electron webview tag 的硬性默认值）**：
- `<webview>` 标签的 `webpreferences.nativeWindowOpen` 默认是 **`true`**（与 BrowserWindow 不同！）
- 当 `nativeWindowOpen=true` 时，guest page 的 `<a target="_blank">` 和 `window.open` 直接走 native
  弹窗流程（开新 BrowserWindow），**完全不触发** webContents 的 `new-window` 事件
- 即使去掉 `allowpopups` 也不行，因为 `nativeWindowOpen` 仍然是 true

**修复**：在 `<webview>` 标签上显式设 `webpreferences="nativeWindowOpen=no"`，让 new-window 事件
冒泡到主进程监听器，由代码自己 preventDefault 并开新 tab。
- `renderer/modules/common/webview-controls.js` `ensurePreviewWebview()`:
  `wv.setAttribute('webpreferences', 'nativeWindowOpen=no');`
- `renderer/modules/common/tabs.js` `openTab()`:
  `wv.setAttribute('webpreferences', 'nativeWindowOpen=no');`

**记忆口诀**：webview 想拦 target=_blank，必须同时满足
1. **不设** `allowpopups`（避免 native 弹窗默认行为）
2. **显式设** `nativeWindowOpen=no`（让 new-window 事件冒泡）

## 终极方案：用 WebContentsView 替代 <webview> 标签（方案 A）

**根因**：Electron 34 Windows 环境下，`<webview>` 标签对 `<a target="_blank">` 的所有应用层拦截
（new-window、setWindowOpenHandler、注入脚本、HTML 属性 webpreferences）**全部失效**。
- `<webview>` 标签的 `webpreferences` HTML 属性**不支持** `nativeWindowOpen`
- 即使主进程拿到 guest webContents 调用 setWindowOpenHandler，webview guest 上也不触发
- 所有 DOM 注入拦截也无效（click 根本到不了页面，native 弹窗流程在引擎层直接接管）

**解决**：用 Electron 主进程 `WebContentsView` API（替代 `<webview>` 标签）。
- `WebContentsView` 的 webContents 是**完整的** webContents
- 主进程 `view.webContents.setWindowOpenHandler({...})` **能正常拦截** target=_blank / window.open
- 多 tab = 多个 WebContentsView 实例，缓存在内存
- 切换 tab 通过 `hostWindow.contentView.addChildView(view)` / `removeChildView`，view 状态保留

**实现清单**：
- 新增 `main/browser-view-manager.js`：BrowserViewManager 类，管理 WebContentsView 多 tab + 拦截
- `main/main.js`：集成 BrowserViewManager，删除 `did-attach-webview` 监听，添加 IPC handler
- `main/preload.js`：新增 `openInAppUrl/openTabInApp/activateAppTab/closeAppTab/setAppBounds/setAppZoom/onAppTabsChanged`
- `renderer/panel.html`：删除 `<webview>` 标签及 `#previewWebviewSlot` 等占位结构
- `renderer/modules/common/webview-controls.js`：重写为 IPC 模式（不再 createElement webview）
- `renderer/modules/common/tabs.js`：重写为 tabBar 渲染 + IPC
- `renderer/modules/recording/internal/webview-recording.js`：`navigateInAppBrowser` 改用 `openInAppUrl` IPC
- `renderer/modules/preview/preview.js` & `step-selector.js`：HTML 预览改用 `openInAppUrl` IPC

**MVP 状态**（2026-08-10）：
- ✅ 应用内多 tab 浏览器（WebContentsView）
- ✅ target=_blank 拦截开新 tab（核心诉求）
- ✅ tabBar 渲染
- ✅ 适配/缩放（用 `setZoomFactor`）
- ⚠️ 录制模式元素选择/凭证填充/HTML 捕获：暂时失效（依赖主进程转发 webContents ipc-message）
- ⚠️ preview 步骤选择器同步：暂时失效（依赖 webview.getURL()）

**bounds 同步**：渲染进程通过 `getBoundingClientRect()` 取 previewContainer 在 contentView
内的坐标，作为 BrowserView 的 bounds。窗口 resize / tabBar 渲染后通过 `setAppBounds` IPC 通知主进程。

## 主进程闭包作用域陷阱（模块变量必须声明在文件顶部）

**症状**：实施 BrowserViewManager 重构后，菜单无法切换、浏览器无法打开。
**根因**：把 `const browserViewManager = new BrowserViewManager(...)` 放在 `createPanelWindow()`
函数内部，导致它是函数作用域变量。`app.whenReady().then()` 里的 `ipcMain.handle()` 闭包访问不到
（虽然语法上能"找到"标识符，但闭包实际捕获的是函数参数或外层模块作用域，函数内 const 是局部）。
**结果**：`ReferenceError: Cannot access 'browserViewManager' before initialization` 或
`undefined is not a function`（具体看 JS 引擎对 TDZ 的处理）。
**修复**：模块顶部 `let browserViewManager = null;`，在 createPanelWindow 中**赋值**而非声明。
**口诀**：主进程跨闭包共享的状态，必须是模块作用域变量（let 在文件顶部），不能在函数内 const。

## ES Module import 死引用导致整个 renderer 崩溃

**症状**：重构 webview-controls.js 后，启动后看不到任何 `[renderer]` 日志（renderer 完全没初始化）。

## executeJavaScript 时序：页面未加载完成时静默失败

**症状**：用户在加载 URL 后立刻点"拾取元素"，页面**仍处于选择模式**（点击无反应）。
**根因**：`tabs.js` 收到 `onAppTabsChanged` 时立刻调 `injectRecordingHelper(tabId)`，
但此时 BrowserView 的 webContents 仍在加载页面（`isLoading()` 为 true）。
`executeJavaScript(code)` 在 page unload 期间会被静默吞掉，`window.__recHelper` 永远没创建。
后续 `enableSelectionMode` 调 `window.__recHelper && window.__recHelper.enableSelectionMode()` 因
`__recHelper` 是 undefined 返回 undefined，但**不抛错**，所以选择模式看似启用实则无效。

**修复**（BrowserViewManager）：
1. `injectRecordingHelper` 检测 `isLoading()`：true 时设 `pendingInject=true`，返回 `{pending:true}` 不抛错
2. view 注册 `did-finish-load` 监听：触发时如果 `pendingInject && !helperInjected` 自动调 injectRecordingHelper
3. `enableSelectionMode` 检测 helper 未注入：先 injectRecordingHelper，pending 时 await `_waitForHelper`
4. `_waitForHelper`：轮询 helperInjected 标志直到注入完成或超时

**经验**：`executeJavaScript` 永远要在 `did-finish-load` 之后调用，否则失败不抛错只静默吞掉。
加载时序判断用 `webContents.isLoading()` 或监听 `did-finish-load` 事件。

## ipcRenderer.sendToHost 是 <webview> 标签专属 API（关键！）

**症状**：BrowserViewManager 用 `view.webContents.on('ipc-message')` 想转发 guest 的 `__recSendToHost` 调用，
**但 ipc-message 事件从不触发**。helper 内部调 `__recSendToHost` 后主进程无反应。
**根因（Electron 文档明确）**：
> `ipcRenderer.sendToHost(channel, ...args)` - This is **only available for the webview tag**.

**WebContentsView 没有 sendToHost 机制**。它会直接抛错或静默失败（取决于 Electron 版本）。
`view.webContents.on('ipc-message')` 监听的是 `ipcRenderer.send` 触发的事件，跟 sendToHost 无关。

**修复**：
1. preload 改用 `ipcRenderer.send('app-bridge-from-view', { channel, data })` —— 普通 IPC 通道
2. 主进程 `ipcMain.on('app-bridge-from-view', (event, payload) => { ... })` 接收
3. 通过 `event.sender` (webContents) 反查 tabId（BrowserViewManager 提供 `findTabIdByWebContents`）
4. 转发到 panelWindow 的 'app-bridge-message' 事件

**口诀**：
- `<webview>` 标签 → guest 用 `sendToHost` → embedder renderer 的 webview DOM event 'ipc-message'
- `WebContentsView` → guest 用 `ipcRenderer.send` + 主进程 `ipcMain.on` → 主进程手动转发到目标 renderer
- 两者 IPC 桥接机制**完全不同**，不要混用

**问题**：WebContentsView 是 OS 级渲染，HTML z-index 无法穿透。任何放在 right column 内的 HTML 弹窗

   - CSS 加 `.preview-loading-inline` 修饰符改为行内布局

**剩余限制**：right column 内其他 UI（如 #rightContent）若需与 BrowserView 重叠，应避免。

## WebContentsView 自适应窗口大小（2026-08-10 晚补）

**问题**：用户拖拽窗口边框 / 调节右栏中间列大小时，BrowserView 不跟随变化。

**根因**：
1. `pushAppBounds` 只监听 `window.resize`（OS-level panelWindow resize），但用 RAF 调度的 renderer resize 在某些场景不触发
2. BVM.setBounds 只更新 active view，切 tab 后未激活 view 用的是创建时初始 bounds

**修复**：
1. **BVM.setBounds → 所有 view**：`for (const [, t] of this.views) t.view.setBounds(bounds)`，避免切 tab 后看到旧 bounds
2. **pushAppBounds 加 ResizeObserver**：监听 previewContainer / rightColumn / mainColumn 的 ResizeObserver，**任一容器尺寸变化即 push bounds**
3. **pushAppBounds 拿到的 rect.width < 1 && height < 1 时不更新**（避免 BrowserView 闪退到 0 大小）

**口诀**：BrowserView bounds 更新要走 ResizeObserver，而非依赖 window resize。

## Preview tab 加载 file:// 失败（2026-08-10 20:48）
