## 二次修复：UA 用 webview `useragent` 属性持久化（根治"刷新回到 PC"）
上一轮的"reload 前重设 setUserAgent"仍无效，根因更深：`<webview>` 标签在【每次导航/reload】时都会按自身的 `useragent` 属性重置本次请求的 UA。仅用 `wc.setUserAgent()`（JS API）会在 reload 时被 webview 自身重置覆盖 → 刷新请求发的是桌面 UA → 站点跳回 PC。且用户刷新常走 webview 自身 F5/右键（不过 App 的 doReload），`setUserAgent` 永远晚于请求发出。
修复（声明式持久 UA，webview 自行注入到每一次请求）：
- renderer/modules/common/webview-controls.js：applyMobileEmulation 现在【先把移动端 UA 写进 `webview.useragent` 属性】（`enabled` 时 setAttribute、`removeAttribute` 还原；加 `cur !== MOBILE_UA/null` 守卫避免重复写触发自动 reload 循环）；保留 `wc.setUserAgent()` + `setTouchEmulationEnabled` 作为兜底。`MOBILE_UA` 改为 `export` 供 tabs 复用。
- renderer/modules/common/tabs.js：import MOBILE_UA；openTab 在首次 `setAttribute('src', url)`【之前】就 `if (appState.isMobileMode) wv.setAttribute('useragent', MOBILE_UA)`，确保新 tab 第一次导航即携带移动端 UA（否则首跳仍是桌面）。
- 验证：node --check 两个 ESM 通过。
- 要点：改用属性后，移动端开关切换 / 地址栏回车 / 分辨率切换 / webview 内 F5 右键刷新 / 新 tab 跳转 全部稳定携带移动端 UA，不再依赖事件时序。

## 三次修复：改用 CDP Emulation（根治 platform 检测 → 重定向回 PC）

## 四次修复（关键）：CDP 命令因 userAgentMetadata 结构违规整体失败
用户贴出站点真实 isMobile()——纯 navigator.userAgent 字符串判断（含 iPhone/Android/HarmonyOS 等即移动端）。由此反推：只要 UA 含 iPhone 就必为移动端；"首次对、刷新错"=UA 覆盖没跨 reload 持久。
根因定位：applyCdpMobile 里 `Emulation.setUserAgentOverride` 传了 `userAgentMetadata`（含 platform/platformVersion/architecture/model/mobile）。该字段结构若不合规，Chromium 会对【整条命令】校验失败并 reject → CDP 的 UA 覆盖根本没生效。结果只剩 `wc.setUserAgent()` 兜底（它只在首次 webview.src 前同步设一次、不跨 reload 持久）→ 刷新请求已发出且用回桌面 UA → 跳 PC。这与"真实浏览器 OK、我们不行"完全吻合（DevTools 命令合规）。
修复：
- renderer/modules/common/webview-controls.js：applyCdpMobile 精简 `setUserAgentOverride` 只传 `{userAgent, platform:'iOS'}`（删掉 userAgentMetadata，消除命令整体失败风险）；attach 显式 '1.3' 并加失败日志；命令加 .then/.catch 日志便于核对。站点只用 UA 字符串判断，platform 足够。
- 验证：node --check 通过。
- 风险：若 CDP 仍不生效（debugger 被占用/被禁），回退到 webview `useragent` 属性 + setUserAgent；属性声明式、跨 reload 持久。若仍不行需用户开 webview devtools 看 console 日志（已加 [panel] 前缀日志）确认覆盖是否生效。

## 根因实测 + 最终修复：UA 覆盖异步竞态（CDP），改用 setUserAgent
用户要求实测那个 UAT 地址、监听为何跳 PC。本机用 Playwright(chromium-headless-shell) 真实加载 `https://xft2-web-home-uat.cmburl.cn/app-home/assets/mhtml/homepage.html` 并监听跳转：

## 录制资源 URL：相对→绝对（不用 base64）+ 内联 style 背景图修复（2026-08-19 17:08）

背景：用户发现录制产物 step1.html 里图片没 base64，追问资源处理逻辑。整理后明确需求：**不做 base64，改为"相对地址→绝对地址"**，并保证移动端页面录制的资源 src 也能访问。

现状链路（应用内 webview 模式）：renderer/webview-recording.js `captureWebviewData()`（canvas→toDataURL 转图，其余 img src 原样、抓 CSS/iframe）→ 主进程 recorder._nextStepWebview → src/html-capture.js `processFromCapturedData()`（CSS 内联 + `_fixResourceUrls` 相对→绝对）→ src/export.js 分文件落盘 step1.html/.css/iframe。

结论：`_fixResourceUrls` 只扫标签属性（img[src]/video/audio/source/iframe/embed/object/track + srcset），**不处理内联 style 属性里的 url()**，所以 `<div style="background:url(./img/x.png)">` 这类背景图导出后仍是相对路径 → file:// 预览/部署后丢失。移动端页面内联背景图尤其常见（本场景 demo_config.json 的 isMobileGuide=true）。

改动：
1. 撤销了上一轮误加的 base64 内联脚本（webview-recording.js 的 imageInlineCode 定义+调用已删，恢复原状，仅保留原有 canvas→toDataURL）。
2. src/html-capture.js `_fixResourceUrls` 末尾新增：`$('[style]')` 遍历，把内联 style 里 `url(...)` 相对→绝对（跳过 data:/http/https/blob/#，用 `new URL(rel, baseUrl)` 解析，baseUrl=页面真实 URL）。
